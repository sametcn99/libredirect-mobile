# Contributing to LibRedirect Mobile

Thanks for your interest in contributing.

## Project language policy

All code, comments, commit messages, UI strings, and documentation in this
repository must be written in English, with no exceptions. (User-facing
translations live in `android/app/src/main/res/values-tr/` for the Turkish
locale and are maintained alongside the English source strings.)

### Translating / Weblate

UI text lives in two files:
`android/app/src/main/res/values/strings.xml` (source of truth, English)
and `android/app/src/main/res/values-tr/strings.xml` (Turkish). Adding or
changing any user-visible string requires updating **both** files in the
same change — a missing translation falls back to English silently, so CI
cannot catch it. Keep format specifiers (`%1$s`, `%1$d`) intact and prefer
full sentences over fragments so word order can be translated. New
locales: copy `values/` to `values-<lang>/`, translate the strings, and add
the language to `android/app/src/main/res/xml/locales_config.xml` and the
in-app language dialog. If you want to contribute a translation at scale,
open an issue so a Weblate project can be set up rather than sending
one-off PRs.

## Repository structure

- `android/app/` — the Kotlin/Compose Android application: navigation,
  settings UI, redirect entry point (`RedirectActivity`), built-in browser,
  manifest repository that regenerates from live upstream data, custom
  services, and the update checker.
- `android/core/` — the pure-Kotlin routing engine: manifest model and
  validator, URL router, template renderer, exception matcher, URL
  utilities, and the upstream converter (`upstream/`). It has no Android
  dependencies, so its tests run on the JVM (`:core:test`).

`android/core` and `android/app` are separate Gradle modules. Changes to one
do not require touching the other, but the manifest contract — expressed in
code by the manifest model and `ManifestValidator` — binds them together.

## Development setup

### Android (`android/`)

Requirements: JDK 17, Android SDK (compileSdk as pinned in
`android/gradle/libs.versions.toml`).

```bash
cd android
./gradlew ktlintCheck detekt      # static analysis
./gradlew :core:test              # routing engine unit tests (JVM)
./gradlew testDebugUnitTest       # app module unit tests
./gradlew assembleDebug           # build the debug APK
```

On Windows, use `gradlew.bat` instead of `./gradlew`.

### Manifest generation

The routing manifest is generated by the app itself (`android/core`'s
`upstream/` package) from live LibRedirect upstream data: `config.json`
from libredirect/browser_extension supplies the service/target/frontend
structure, `data.json` from libredirect/instances the instance lists. The
generator follows a strict "never guess" principle: a target, frontend, or
service that cannot be converted with full confidence is dropped and
reported, not approximated. Generation runs on app start (throttled), via
the manual refresh, and via the opt-in daily worker; every result must pass
validation and a self-test before it is activated atomically. The manifest
committed at `android/app/src/main/assets/routes.json` is only the
first-start/offline fallback and is never hand-edited.

## Architectural invariants

These rules exist to keep the security model intact. A PR that violates
them will be rejected regardless of other merits:

1. **No remote code execution.** The manifest can only express the routing
   primitives the app already implements — the sealed `Strategy` type in
   `android/core` (`replace-origin`, `template`, `custom-scheme`,
   `passthrough`). There is deliberately no expression/eval variant; adding
   a new primitive is a coordinated change across `core`, the validator,
   the upstream converter, and an app release.
2. **Generation converts, never interprets.** A manifest refresh regenerates
   the manifest from exactly the two fixed upstream sources via the
   `android/core` `upstream/` converter, and only the fixed allowlisted
   strategies can appear in the result. Anything the converter cannot map
   with full confidence is dropped and reported — never guessed. Every
   result must pass the validator and self-test before activation.
3. **Fail-open routing, fail-safe updates.** Routing failures open the
   original URL; malformed or unsupported-scheme input is dropped. A failed
   manifest update never touches the last known good manifest.
4. **No new network endpoints without review.** The app currently talks to
   exactly three upstream sources (`libredirect/browser_extension`
   `config.json` and `libredirect/instances` `data.json` for manifest
   generation, GitHub Releases API for the update check) plus whatever the
   user browses to in the built-in browser. Anything else requires an
   explicit justification in the PR.
5. **No telemetry.** No analytics, tracking, or crash-reporting SDKs.

## Code style

- Kotlin: enforced by ktlint and detekt (`./gradlew ktlintCheck detekt`).
  Detekt runs with `buildUponDefaultConfig`; do not suppress rules without a
  written justification next to the suppression.
- Match the surrounding code's comment density and idiom. Document *why*
  comments explain a non-obvious constraint, not *what* the code does.

## Tests

- Routing-engine behavior belongs in `android/core/src/test/` — these are
  fast JVM tests and the right place for route matching, template
  rendering, instance selection, and manifest validation coverage.
- App-level behavior (settings, browser data, parsers) belongs in
  `android/app/src/test/`.
- Upstream-converter changes (`android/core` `upstream/`) ship with cases in
  `android/core/src/test/` — real upstream patterns and the exact expected
  conversion, including the ones that must be refused.
- New routing behavior must ship with tests before the PR is reviewed.

## Pull requests

- Keep changes focused; avoid mixing unrelated refactors with feature work.
- Run the relevant lint/format/test commands above before opening a PR —
  CI (`android-ci.yml` for `android/**`) enforces the same checks.
- Explain the *why* in commit messages and PR descriptions, not just the
  *what*.
- PRs that touch `android/core`, the manifest model/validator, or the
  upstream converter should call out any security-relevant effect explicitly.

## Releases

Maintainers release as follows (there is no manual tagging):

1. Bump `versionName` and `versionCode` in `android/app/build.gradle.kts`.
   The version display reads `BuildConfig` at compile time, so no other
   file needs the same numbers.
2. Commit, then dispatch the `Android Release` GitHub Actions workflow
   (`workflow_dispatch`). It reads the version from the build file, builds
   and signs the APK, smoke-tests the bundled manifest inside the release
   APK, and publishes a GitHub Release tagged `v{versionName}` together
   with a SHA-256 checksum file.
3. New services and frontends reach users through runtime manifest
   generation and need no release by themselves; a release is only required
   when the converter, the routing primitives, or the app itself change
   (see "Manifest generation" above).

## Reporting security issues

Do not open a public issue for security vulnerabilities. See
[SECURITY.md](SECURITY.md).
